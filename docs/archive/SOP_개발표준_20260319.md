## 1. 브랜드 컬러 규칙

### 핫핑크 기준 팔레트
```
주색: #f82b60
hover: #db2456
밝은 배경: bg-rose-50
밝은 테두리: border-rose-100, border-rose-200
그림자: shadow-rose-200, shadow-rose-500/30
링: ring-rose-50
```

### 적용 원칙
- **블루 계열(`blue-*`) 사용 금지** — 신규 코드에서 일절 사용하지 않는다
- `text-blue-*` → `text-[#f82b60]`
- `bg-blue-500`, `bg-blue-600` → `bg-[#f82b60]`
- `hover:bg-blue-*` → `hover:bg-[#db2456]`
- `bg-blue-50` → `bg-rose-50`
- `border-blue-*` → `border-[#f82b60]` 또는 `border-rose-200`
- `focus:ring-blue-*` → `focus:ring-[#f82b60]`
- `shadow-blue-*` → `shadow-rose-*`
- `group-hover:bg-blue-*` → `group-hover:bg-rose-50`
- `group-hover:text-blue-*` → `group-hover:text-[#f82b60]`

### 예외 허용 컬러 (브랜드 무관)
- `red-*` — 삭제, 경고, 위험 액션 전용
- `amber-*`, `emerald-*`, `purple-*` — 프리미엄 라운지 섹션 카드 전용
- `orange-*` — 광고 스폰서 카드 전용
- `gray-*` — 일반 UI 뉴트럴

### 확인 방법
```bash
# 블루 잔류 여부 일괄 점검
grep -r "blue-" src/ --include="*.tsx" -l
```

## 2. 컴포넌트 분리 원칙

### 언제 분리하는가
- 단일 파일이 **300줄 이상**이면 분리 검토
- 파일이 **500줄 이상**이면 분리 필수
- 탭/섹션 단위로 독립적인 state를 가지는 경우 분리

### 분리 순서 (중요)
1. **외부 state 의존 없는 것부터** 먼저 분리
2. **내부 state는 해당 컴포넌트 안으로** 이동 (부모에서 prop drilling 금지)
3. 분리 완료 후 **한 번에** 스타일 교체 (중간에 색상 교체 작업 섞지 말 것)
4. 분리 직후 원본 파일에서 인라인 코드 제거 + import 추가까지 **한 세트**로 처리

### 폴더 구조 규칙
```
app/[feature]/
  page.tsx          ← 라우팅만, 비즈니스 로직 최소화
  [Feature]Content.tsx  ← 실제 컨텐츠 (필요 시)
  components/
    Tab[Name].tsx   ← 탭 단위 분리
    [ComponentName].tsx
```

### 분리 시 금지 사항
- 분리 도중 스타일(blue→hotpink) 동시 변경 금지 — 작업 단계를 나눠라
- 분리 후 원본 파일에 인라인 코드 남겨두기 금지
- 미사용 import 방치 금지

## 3. 스크롤 락 사용 규칙

> ⚠️ **이 섹션은 2026-03-19 실제 운영 장애 원인 분석 결과입니다. 반드시 읽으세요.**

### 장애 요약
- **증상**: 모바일에서 광고 클릭 후 스크롤 영구 멈춤, 커뮤니티 햄버거 카테고리 선택 후 스크롤 멈춤
- **원인 1**: `useBodyScrollLock` cleanup 함수에서 `touchAction`, `overscrollBehavior` 미해제
- **원인 2**: `JobDetailModal`이 `useBodyScrollLock(true)` 하드코딩 + 부모(`HomeClient`)도 동시 호출 → 카운터 2 → 해제 불일치
- **원인 3**: 커뮤니티 햄버거 메뉴에서 `router.push()` → `setShowMobileMenu(false)` 순서가 반대 → 네비게이션으로 컴포넌트 언마운트 시 cleanup 경로로 진입

### 올바른 useBodyScrollLock 사용법

#### ✅ 올바른 패턴 — 부모가 관리, 자식은 호출 금지
```tsx
// 부모 컴포넌트 (HomeClient.tsx 등)
useBodyScrollLock(!!selectedShop || showPaymentPopup);

// 자식 모달 컴포넌트 (JobDetailModal.tsx 등)
// → useBodyScrollLock 호출 안 함. 부모가 이미 관리함.
export const JobDetailModal = ({ onClose }) => {
    // NO useBodyScrollLock here
};
```

#### ❌ 금지 패턴 — 중복 호출
```tsx
// 부모
useBodyScrollLock(!!selectedShop);  // count = 1

// 자식 (마운트 시점에 추가 호출)
useBodyScrollLock(true);  // count = 2 → 닫힐 때 count 불일치 위험
```

#### ✅ 조건부 렌더링으로 열린 모달 제어하는 경우
```tsx
// 모달이 조건부 렌더링되는 경우(항상 true인 경우)라면
// 부모에서 관리하는 것이 원칙
{selectedShop && (
    <JobDetailModal ... />  // 이 컴포넌트 내부에서 useBodyScrollLock 호출 금지
)}
```

#### ✅ 독립 모달(부모 관리 없음)인 경우
```tsx
// PaymentPopup처럼 isOpen prop을 받는 경우만 자체 호출 허용
export const PaymentPopup = ({ isOpen, onClose }) => {
    useBodyScrollLock(isOpen);  // isOpen prop 기반으로 호출 → OK
};
```

### 네비게이션 + 모달 닫기 순서 규칙
```tsx
// ✅ 올바른 순서 — 상태 먼저 닫고, 라우팅 나중
onClick={() => {
    setShowMobileMenu(false);   // 1. 먼저 상태 해제 (스크롤락 해제 트리거)
    router.push('/some-path');  // 2. 그다음 라우팅
}}

// ❌ 금지 순서
onClick={() => {
    router.push('/some-path');  // 라우팅 먼저 → 컴포넌트 언마운트 → cleanup 경로
    setShowMobileMenu(false);   // 이미 언마운트돼서 실행 안 됨
}}
```

### useBodyScrollLock 훅 수정 시 체크리스트
훅을 수정할 일이 생기면 아래 세 경로를 **모두** 확인:
- `if (isOpen)` 브랜치: 락 걸 때 적용한 스타일
- `else` 브랜치: 정상 닫힘 시 해제
- `return () => {}` (cleanup): 언마운트 시 해제 ← **여기서 빠뜨리는 경우가 많음**

세 경로의 **적용/해제 속성 목록이 완전히 일치**해야 함:
```ts
// 적용 속성 목록
document.body.style.overflow = 'hidden';
document.body.style.touchAction = 'none';       // 모바일
document.body.style.overscrollBehavior = 'none'; // 모바일
document.body.style.paddingRight = `${scrollBarWidth}px`; // PC

// 해제 속성 목록 (else + cleanup 모두 동일하게)
document.body.style.overflow = '';
document.body.style.touchAction = '';
document.body.style.overscrollBehavior = '';
document.body.style.paddingRight = '';
document.body.classList.remove('modal-open');
```

## 4. 모달 구현 규칙

### createPortal 사용 원칙
- 헤더 위에 떠야 하는 모달 → `createPortal(…, document.body)` 필수
- z-index 계층:
  ```
  일반 콘텐츠: z-0 ~ z-10
  헤더: z-40
  일반 모달: z-50
  전역 모달(로그인 등): z-[20000]
  최우선 모달(접근제한 등): z-[99999]
  ```

### SSR 안전 처리
```tsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);

// createPortal은 mounted 이후에만
{mounted && someModalOpen && createPortal(<Modal />, document.body)}
```

### 모달 닫기 처리 규칙
- 배경 클릭 시 닫힘: `onClick={() => setOpen(false)}` on backdrop
- ESC 키 닫힘: `useEffect`로 `keydown` 이벤트 등록 권장
- 닫기 버튼: 항상 우상단 X 버튼 제공

## 5. 라우팅 & 네비게이션 규칙

### useSearchParams 사용 규칙
> ⚠️ **빌드 에러 원인 — 반드시 지킬 것**

`useSearchParams()`를 사용하는 컴포넌트는 **반드시 Suspense로 감싸야** 함. 그렇지 않으면 정적 빌드(Vercel 배포) 시 `/404` 생성 실패로 **전체 빌드 실패**.

```tsx
// ✅ 올바른 패턴
export default function Page() {
    return (
        <Suspense fallback={<div>로딩 중...</div>}>
            <PageContent />  {/* useSearchParams 사용하는 컴포넌트 */}
        </Suspense>
    );
}

// ❌ 금지 패턴
export default function Page() {
    const searchParams = useSearchParams();  // Suspense 없이 직접 사용 → 빌드 실패
    ...
}
```

### 적용 대상 파일 확인 방법
```bash
grep -r "useSearchParams" src/ --include="*.tsx" -l
# 검색된 파일들이 모두 Suspense 안에 있는지 확인
```


## 6. 빌드 & 배포 규칙

### 배포 전 로컬 빌드 확인 필수
```bash
npm run build
# ← 성공 확인 후 push. 빌드 실패 상태로 push 금지.
```

### 흔한 빌드 실패 원인 & 해결책

| 에러 | 원인 | 해결 |
|------|------|------|
| `useSearchParams() should be wrapped in a suspense boundary` | Suspense 미적용 | 해당 컴포넌트를 `<Suspense>`로 감싸기 |
| `Module not found` | import 경로 오타, 파일 삭제 후 import 잔류 | 미사용 import 제거, 경로 확인 |
| `Type error` | TypeScript 타입 불일치 | 타입 맞추거나 적절히 캐스팅 |

### Vercel 환경변수 관리
```
NEXT_PUBLIC_AUDIT_MODE=false   ← 운영환경, 임시막 해제
NEXT_PUBLIC_ADULT_GATE_DISABLED=false  ← 성인인증 게이트
```
- 환경변수 변경 시 Vercel 대시보드에서 변경 후 **Redeploy 필수**
- `NEXT_PUBLIC_*` 변수는 클라이언트 번들에 포함됨 — 민감 정보 절대 금지

### 배포 실패 시 대응 절차
1. Vercel 대시보드 → 해당 배포의 빌드 로그 확인
2. 에러 메시지 복사 → 원인 분석
3. 로컬에서 `npm run build`로 동일 에러 재현 후 수정
4. 수정 후 commit & push → 자동 재배포 확인

## 7. Git 운용 규칙

### 커밋 메시지 규칙
```
[FEAT] 새 기능 추가
[FIX]  버그 수정
[UPDATE] 기존 기능 개선
[STYLE] UI/스타일 변경 (기능 변경 없음)
[REFACTOR] 코드 구조 개선 (기능 변경 없음)
[HOTFIX] 운영 긴급 수정
```

### Git Stash 사용 금지
> ⚠️ **이전 세션에서 stash pop으로 수정 내용이 롤백된 사고 발생**

- `git stash` 사용 금지 — 작업 중 브랜치 전환 필요 시 commit 후 전환
- 불가피하게 stash 사용 시 `git stash list`로 내용 확인 후 처리
- stash pop 후 반드시 `git diff HEAD`로 롤백 여부 확인

### 커밋 전 체크
```bash
git status          # 변경된 파일 목록 확인
git diff --stat     # 변경 내용 요약 확인
npm run build       # 빌드 성공 확인
git add [파일들]    # 개별 파일 추가 (git add . 지양)
git commit -m "[TYPE] 설명"
```

## 8. 접근 제어 & 인증 규칙

### userType 분류
```ts
type UserType = 'individual' | 'corporate' | 'admin' | 'guest';
// individual: 개인(구직자) 회원
// corporate:  업체(사장님) 회원
// admin:      관리자
// guest:      비로그인
```

### 페이지별 접근 제어 패턴
```tsx
// 가이드 페이지 시작하기 버튼 기준
const handleStart = () => {
    if (!isLoggedIn) { router.push('/?page=login'); return; }
    if (userType === 'individual') { alert('업체회원만 이용 가능한 서비스입니다.'); return; }
    router.push('/my-shop');  // corporate, admin 모두 이동
};
// → admin을 individual과 같이 처리하지 말 것
```

### 커뮤니티 접근 제어
- `guest`: 글 목록 보임, 클릭 시 로그인 유도
- `individual`: 전체 이용 가능
- `corporate`: 읽기 금지 (접근제한 모달)
- `admin`: 전체 이용 가능

## 11. 세션 & localStorage 규칙

> ⚠️ **이 섹션은 2026-03-19 운영 장애(쪽지함 받은/보낸 동일 내용, MY 버튼 플리커링) 원인 분석 결과입니다.**

### Mock 세션 저장 구조

```ts
// Mock 로그인 시 저장되는 키 (useAuth.ts의 login() 함수)
localStorage.setItem('coco_mock_session', JSON.stringify({
    type: 'corporate' | 'individual' | 'admin',
    id: 'test_shop',
    name: '테스트 사장님',
    nickname: '번창하는조사장',
    credit: 1000,
    points: 500,
    email: 'test@example.com'
}));
```

### localStorage 키 우선순위 규칙

어떤 컴포넌트에서든 현재 로그인한 사용자 정보를 localStorage에서 읽어야 할 때:

```ts
// ✅ 올바른 우선순위 (순서 반드시 준수)
// 0순위: coco_mock_session (Mock 로그인 — 대부분의 개발/테스트 환경)
const mockSession = localStorage.getItem('coco_mock_session');
if (mockSession) {
    const parsed = JSON.parse(mockSession);
    name = parsed.nickname || parsed.name;
}

// 1순위: user_name (실서비스 직접 저장 키)
// 2순위: user_session (JSON 형태 실서비스 세션)
// 3순위: shop_title (업체명 폴백)

// ❌ 금지 패턴 — coco_mock_session을 무시하고 다른 키만 탐색
const name = localStorage.getItem('user_name') || '회원';
// → Mock 로그인 시 항상 '회원'이 되어 쪽지함 받은/보낸 동일 데이터 표시
```

### 왜 coco_mock_session이 최우선인가

| 환경 | 로그인 방식 | 저장 키 |
|------|-----------|---------|
| 개발/테스트 | Mock (admin_user, test_shop 등) | `coco_mock_session` |
| 실서비스 (Supabase) | signInWithPassword | `user_name`, `user_session` 등 |

→ 개발/테스트 환경에서는 `coco_mock_session`만 존재. 이를 최우선으로 확인하지 않으면 실질적으로 모든 개발/테스트가 비정상 동작.

### 쪽지함(MessageModal) userName 패치 이력

- **증상**: 받은쪽지함과 보낸쪽지함에 동일한 쪽지가 표시됨
- **원인**: `MessageModal.tsx`에서 `user_name`, `user_session`, `shop_title` 순으로만 탐색 → Mock 로그인 시 userName = '회원' → `NoteService.getInbox('회원')` = `NoteService.getSent('회원')` → 동일 결과
- **수정**: `coco_mock_session`을 0순위로 탐색하도록 변경 (2026-03-19)
- **영향 범위**: `src/components/message/MessageModal.tsx`

## 12. 네비게이션 바 & 하단 탭 규칙

> ⚠️ **이 섹션은 2026-03-19 MobileBottomNav MY 버튼 플리커링(로그인 화면 ↔ 마이페이지 왔다갔다) 장애 원인 분석 결과입니다.**

### 장애 요약

- **증상**: 업체회원으로 로그인 후 하단 MY 버튼을 누르면 마이페이지 대신 로그인 화면이 뜨거나, 여러 번 누르면 마이페이지 ↔ 로그인 화면이 교대로 나타남
- **원인 1**: `MobileBottomNavContent`가 `const { userType } = useAuth()`만 구독. `isLoggedIn`, `isLoading` 미사용
- **원인 2**: MY 버튼 onClick 조건이 `if (!mounted || !userType || userType === 'guest')` → `mounted`의 초기값이 `false` → 첫 클릭 시 로그인 페이지로 이동
- **원인 3**: `useAuth()` 초기화 중 `userType`이 잠깐 'guest' → 그 타이밍에 클릭하면 로그인 페이지

### 올바른 인증 상태 확인 패턴

```tsx
// ✅ 올바른 패턴 — isLoggedIn + isLoading 사용
const { userType, isLoggedIn, isLoading } = useAuth();

onClick={() => {
    if (isLoading) return;  // 세션 로딩 중이면 아무것도 하지 않음
    if (!isLoggedIn || userType === 'guest') {
        router.push('/?page=login');
    } else {
        router.push('/my-shop');
    }
}}

// ❌ 금지 패턴 — mounted + userType 조합
onClick={() => {
    if (!mounted || !userType || userType === 'guest') {
        // mounted 초기값 false → 첫 렌더 즉시 로그인 페이지
        // userType은 세션 로딩 전에는 항상 'guest' → 레이스 컨디션
        router.push('/?page=login');
    }
}}
```

### 인증 상태 확인 우선순위

```ts
// useAuth()가 반환하는 값 사용 (신뢰 순서)
const { isLoggedIn, isLoading, userType } = useAuth();

// 1순위: isLoading — true면 아직 세션 판단 불가. 아무것도 하지 말 것
// 2순위: isLoggedIn — 실제 로그인 여부 (mock + Supabase 통합)
// 3순위: userType — 역할 구분 (로그인 여부는 isLoggedIn으로 확인 후 사용)
```

### 하단 탭바(MobileBottomNav) 구현 규칙

- **조건부 항목 라벨**: `mounted && userType === 'individual'` 처럼 `mounted` 조건은 UI 표시에만 사용
- **클릭 핸들러**: `isLoading`, `isLoggedIn`으로 판단. `mounted`에 의존 금지
- **admin 탭 구성**: `userType === 'admin'` 일 때 다른 navItems 배열 반환 (현재: 홈/통계/회원관리/심사/설정)

### 관리자 모바일 메뉴 규칙

```tsx
// ✅ 올바른 패턴 — admin이면 어느 페이지에서도 햄버거 메뉴 표시
{isMounted && userRole === 'admin' && isLoggedIn && !isLoading && (

// ✅ admin 전용 햄버거 메뉴 최상단 섹션 — 로그아웃 버튼 포함 필수

    </div>

```
